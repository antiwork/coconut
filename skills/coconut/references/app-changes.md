# Changing the Coconut app (iPhone, Mac, service)

The source is `antiwork/coconut`, checked out at `~/Projects/coconut`. The install folder `~/Coconut` is not the place to edit.

## Procedure

1. Confirm the request against `origin/main` before saying anything about current behavior. A person who describes how the app works ("+ opens a new chat with a random letter") may be describing the change they want. `git fetch origin main` and `git grep ... origin/main -- ios mac backend` show what the app does today.
2. Check that no open PR or branch already does it: `gh pr list -R antiwork/coconut --state open`.
3. Work in a fresh worktree: `git worktree add -b <topic> ~/Projects/coconut-wt-<topic> origin/main`. The main checkout often holds another session's uncommitted work on another branch; never stash or reset it.
4. Follow `AGENTS.md`: no tests and no test suites; check the change by hand (see below), then commit straight to `main`; no PR unless the person asks. Commit messages describe the resulting behavior. Prefer deleting code that the change makes unused.
5. Most UI flows exist twice: iPhone (`ios/Coconut/*.swift`, e.g. `CoconutApp.swift` root toolbar) and Mac (`mac/Sources/CoconutMac/MacMainWindow.swift`). Put shared logic in an `AppStore` extension and call it from both. The iPhone tab bar always has exactly five tabs (`HomeTab`): a sixth makes iOS add a More tab, which the person does not want, so a new place goes on the page of a tab or takes the place of one. The tabs are Finance, Support, Product, Chats and You, in that order (the person's list: for a day the tabs began with Product and Finance was called Business, and the person put Finance first again), and each holds only its own things: Finance its to-dos (the label `finance`) with each risk review past SLA as a row of its own, which the person decides in the app with the choices of a poll and Gumclaw carries out through an `@gumclaw` issue of gumroad-private (`RiskReviews.swift`, `backend/coconut/risk_reviews.py`), then the overview with the risk reviews, Accounting, Marketing and History; Support its to-dos and the customer queue, where the person responds to a conversation with the options of a poll (Let Gumclaw answer, Refund and answer, Close without answer) that Gumclaw carries out through an `@gumclaw` issue, or with an answer of their own (`SupportHandoffs.swift`, `backend/coconut/support_handoffs.py`); Product the cards, Needs attention, its to-dos and the open pull requests; Chats every agent and every chat with people; You the person, this device and the settings (the Mac, notifications, connections, usage, the team, the repositories that Coconut follows). An issue is a to-do of one list, so no tab lists the issues of another (Support shows no queue of all issues, Finance no pull requests). The Mac sidebar has no Product row: the person chose on a card to leave it as it is (2026-11-24), so the Mac's Home keeps the cards and its Support keeps the queue of the product issues; do not add the row or offer it again. Chats has the sections of Slack (`ChatList.sections`): one for each project, Coconut first, then Team chats, Other agents, Personal at the bottom and Archived last; each starts folded, and a folded section still shows its real work (see the Chats rule below). A conversation with the agent of a project is an agent in every label (New agent, Archive agent, the section Other agents of Chats and of the Mac sidebar), and chat names a conversation with people (Team chats, a direct chat) and the tab that holds both; code names such as `HomeTab.chats`, `HomeTab.finance` and `NewChatBar` stay. Buttons and the tint of the app are coconut brown (`BoardStyle.control` in Swift, `accent-color` on the root of the Exact app), and an unread badge is the green of the New line: never black (`Color.primary`) or the system blue, because the person rejects black buttons.
   Nothing links out of Coconut: the person reads, answers, closes and merges in the app, and agents do the same work there. An issue or a pull request opens as `GitHubItemView`, a support conversation as `SupportConversationView` with its answer box, and `stackRoutes` on each navigation stack sends every link of those kinds to these pages (`InAppLink`). The box under an issue, a pull request or a support conversation is the message box too (`ReplyBox`; the person: "comment box can merge w this new agent chat box"): its chip sends the text as the comment or the answer, as the first message of a new chat of a project with the item on top, or to a team agent such as Gumclaw, so an agent starts from the page of its item, with no separate sheet. Any other web page opens in the browser of the app on an iPhone (iOS 26). A new place that shows a GitHub issue, a pull request or a Gmail thread pushes its route, never `Link` to github.com or Gmail, and a new navigation stack wears `stackRoutes` and `InAppDestinations`.
6. When the change works, rebase onto the latest `origin/main`, `git push origin HEAD:main`, and confirm `git rev-parse HEAD origin/main` match. Revert a change that is confirmed broken, then fix forward.
7. Remove the worktree and its branch. Report: the commit, what changed, what was verified (demo mode vs real Mac service), and whether it has reached the person's devices (see "Releases" below). Never say a push to `main` ships by itself without checking.

## Releases

How builds reach devices changes: read `CONTRIBUTING.md` and `git ls-tree origin/main .github/workflows/` before you promise or trigger a release. Your local checkout can still have workflow files that `main` deleted, and `gh workflow run` then fails with a 422. Do not release: an agent publishes the Mac app and TestFlight builds on a loop a couple of times a day. Say plainly in the reply that the fix is on `main` but not on the devices yet.

## A bug report about the person's own data (counts, read state, lists)

The person sees the installed service, not `main`. Before you write a fix:

1. Grep `origin/main` and `git log origin/main -- <module>` for a recent fix; a rewrite often landed hours ago, and only parts of the request (here a colour) remain to do.
2. Compare with the code that runs: `~/Coconut/backend/coconut/` is the installed service. When it lacks the module or still has the old logic, the cause is the old build. When `coconut status` shows a `Pending install` for hours, check that `~/Coconut/.coconut-install.json` exists: without that marker the app treats the folder as a developer checkout, and `deploy.py` refuses it, so the service never updates.
3. Read the live data read-only: `sqlite3 -readonly ~/Coconut/.runtime/host/coconut.sqlite3` (tables `bots`, `messages`, JSON in `data`). Request results are in `.runtime/host/logs/service.log` as `coconut.request_timing` lines.
4. Prove the fix on real data without touching it: `sqlite3 <live db> ".backup $TMPDIR/copy.sqlite3"`, load the module from the worktree with `importlib.util.spec_from_file_location`, run it against the copy with `/opt/homebrew/bin/python3.14`, print before and after per row, then delete the copy. Put that table in the report.

## The requested feature is already on main

A short request ("Coconut needs to be X") is often for something that landed hours ago but has not reached the person's devices. Step 1 finds it: grep `origin/main` for the feature words and list `docs/` and the top folders of `ios/` (a feature usually has its own doc and target folder). Then build nothing, and answer what the person needs: is it on their Mac and their iPhone?

1. Find the commit and its build number. A build number is the commit count: `git log origin/main --format='%h %s' -- <feature paths>`, then `git rev-list --count <sha>`.
2. Mac: compare with the `Coconut.app` line of `coconut status` (build in parentheses) and with the newest `<sparkle:version>` of `https://coconut-updates.gumroad.workers.dev/mac/appcast.xml`. An installed build at or above the feature's has it. When the feed is ahead of the app, automatic updates install it within the hour (or `coconut update`); check again before replying, since the app often updates while you look.
3. iPhone: a green TestFlight run does not mean an upload. Releases coalesce, so most runs end with the `upload` job `skipped`. Walk `gh run list -R antiwork/coconut -w TestFlight` newest first and read `gh run view <id> --json jobs` until a run has `upload` = `success`; that run's head SHA is what the phone can get. `git merge-base --is-ancestor <feature sha> <run sha>` says whether it holds the feature.
4. Confirm the installed part with evidence, not from the doc: for an app extension, `ls Coconut.app/Contents/PlugIns` and `pluginkit -m -v -i <extension bundle id>`.
5. Report per device: on it now, or which build brings it and whether that upload is running. Add any first-use step that the feature's doc names (e.g. open the app once, enable the extension in System Settings). Say what you did not see with your own eyes (a menu you could not open).

## Rules of the screens

These rules came out of the audits of the screens (the information architecture, the business dashboards and the iPhone app). They hold for each new screen.

- Text is data. A number shows with its name only: no eyebrow, no headline that sells, no note or caption that repeats the title, and no legend for a chart that draws one number for each bar.
- Sentence case in each title, menu and button ("Copy link", not "Copy Link").
- One look for one meaning. The dotted circle is work that runs. A tile that opens a screen of the app has a chevron or nothing, never "↗".
- One loading state and one failed state for each page that loads: `BoardLoading` and `BoardLoadNotice`, with one way to try again.
- Each wait shows the coconut, `CoconutLoader` in the size of its place (a page, a row, a button, the working line of a chat), never a system spinner. A ProgressView does not build: `ios/Coconut/CoconutLoader.swift` hides it (the person, 2026-11-25: "add way more personality and brand enforcement to coconut 3 dots").
- Things update instantly and optimistically, so nobody refreshes to see a change (the person, 2026-11-25: "Make it so things update instantly and optimistically so one does not need to refresh to see changes on GitHub Gmail finance chat and others. All instant vibes."). A page that shows data of GitHub or Gmail reads it again when the Mac says that it changed (`business_changed` of the updates, from `backend/coconut/business_watch.py`, which bumps `AppStore.businessChanges`), and an open issue, pull request or support conversation also reads every 10 seconds (`.liveReload`). A write of the person shows at once: a comment or an answer at the end of its page, lighter until it is confirmed, a close or a reopen in its new state, a moved to-do in its new list, and a failure puts it back with the reason. A new page of GitHub or Gmail keys its load on `businessChanges` and carries `.liveReload` when it shows one item; a new write shows its result before the answer. Pull to refresh stays, but nothing may need it.
- A page of tiles is a `BoardPage`. The business dashboards use the one grid and the one tile of `ios/Coconut/Bento.swift` (`BentoGrid`: 12 columns at a Mac width, 2 at an iPhone width), Swift Charts, and the colors of Coconut.
- A dashboard is one page with no scrolling, and a tap on a tile or a row shows more (the person, 2026-11-25: "Simplify dashboards to one page with no scrolling and tapping a box/card / row shows more detail"). Finance and Support show every tile at once (`DashboardPage` in `Bento.swift`): the rows of the grid share the height between the title and the message box. A list is a tile of the rows that fit, and its last line opens the whole list (`TodoTile`). Each tile opens its detail on a page of its own (`BusinessRoute`): GMV opens History, the money Accounting, the risk reviews Risk, the volume and the open conversations of Support its conversations, and its closed conversations and times to resolution how fast and by whom they closed (`SupportDetailView`). A detail page scrolls. A new number of a dashboard goes into a tile that fits or into the detail of a tile, never under the fold.
- A pushed page on an iPhone has its title in the bar. The count of a section counts its rows.
- No settings screens. The person changes a setting by asking the Coconut chat (`coconut_settings`); a setting of one device goes in that chat's bar menu or in You. A new preference never gets a screen, a gear or a toggle. A setting that the person asked to change in one tap is a menu row of You that opens its choices in place (`AutoArchiveMenu`, `BoardRow(menu: true)`), and the Coconut chat changes it too.
- No tabs or toggles inside a page (the person, 2026-11-24: "remove the tab/toggle ui. From all pages as no one will tap those"). A page shows one view: no segmented control, no row of filter chips, no tab row of text. Put what a segment hid on the same page, one part under the other or merged into one list with a label on each row (Support's two queues on the Mac, the review queues of Risk, the cuts of History), or keep only the useful default (the last 30 days of Usage, the open work and the open conversations). A choice that a form needs to work (the project of a new to-do, a notification level) is a menu, not a tab. The tab bar of the iPhone and the sections of the Mac sidebar are places, not tabs of a page. The one filter is the person's own request of that evening ("Ability to show working only from chats top right"): the Working button at the top right of Chats (`WorkingFilterButton`), a button of the bar, not a control inside the page. On, Chats lists only the chats that work or whose card waits (`AppStore.botWorks`) in one list without section titles, and its title says Working. Keep it, and add no other filter on its model.
- The grid of the agents that work (`ChatGridView`, the person: "go to the multitasking view which makes it easy in a grid to see all agents working at once"): the button beside Working at the top right of Chats shows a card for each agent chat that works or whose card waits, all at once, each card the row of its chat over a live copy of the chat. A tap zooms into the chat, as a card of the deck does; Done, a tap beside the cards or a pull down closes it. It is the deck's request with `grid: true` (`ChatDeckRequest`), so a long press on a row still shows the deck of every chat. On the Mac (the person chose it on a card), View > Show working agents with Option-Command-\, beside Show all agents with Shift-Command-\, shows it over the main window (`ChatDeckCommands`, `.showChatGrid`); Escape or the same command closes it, and a scroll past the top does not, because a trackpad swipe would close it by mistake. You → Live is a separate page (tiles with the command, the file, the helpers and the spend, and the teammates who are active).
- A Send of the message box (`NewChatBar`) never opens the chat that it makes. The chat counts at once in the row of its section in Chats, which the list scrolls into view, and shows in its section of the Mac sidebar, also a folded one. The box keeps the keyboard and the cursor, so the person can queue up many chats in a row (`AppStore.newChatSend`, `NewChatReveal`, and `afterStart` in `exact/app.contract`). ## Check by hand

The repository has no tests, and `AGENTS.md` asks for none. Check the change by hand before the push.

The iPhone app: `python3 scripts/qa.py <place>` builds what changed, installs it in its own simulator ("Coconut QA") and opens the app on one screen with demo data. `qa.py open <place>` opens another screen without a build, and `qa.py shot [file]` saves a screenshot. A place is a name of the `--open` launch argument (`showPreviewPlace` in `ios/Coconut/CoconutApp.swift`). Further launch arguments: `--team-preview` (a team with notices), `--attention-preview` (Needs attention), `--bottom` (the end of a page) and `--scrolling` (a chat during a scroll). The same steps by hand, in your own simulator:

```sh
xcodegen generate --spec ios/project.yml            # after adding a Swift file
cd ios
xcodebuild build -project Coconut.xcodeproj -scheme Coconut \
  -destination 'platform=iOS Simulator,id=<udid>' -derivedDataPath $TMPDIR/dd CODE_SIGNING_ALLOWED=NO
xcrun simctl install <udid> $TMPDIR/dd/Build/Products/Debug-iphonesimulator/Coconut.app
xcrun simctl launch <udid> com.gumroad.coconut --demo
xcrun simctl io <udid> screenshot $TMPDIR/shot.png
```
