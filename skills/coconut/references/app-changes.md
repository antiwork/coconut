# Changing the Coconut app (iPhone, Mac, service)

The source is `antiwork/coconut`, checked out at `~/Projects/coconut`. The install folder `~/Coconut` is not the place to edit.

## Procedure

1. Confirm the request against `origin/main` before saying anything about current behavior. A person who describes how the app works ("+ opens a new chat with a random letter") may be describing the change they want. `git fetch origin main` and `git grep ... origin/main -- ios mac backend` show what the app does today.
2. Check that no open PR or branch already does it: `gh pr list -R antiwork/coconut --state open`.
3. Work in a fresh worktree: `git worktree add -b <topic> ~/Projects/coconut-wt-<topic> origin/main`. The main checkout often holds another session's uncommitted work on another branch; never stash or reset it.
4. Follow `AGENTS.md`: no tests and no test suites; check the change by hand (see below), then commit straight to `main`; no PR unless the person asks. Commit messages describe the resulting behavior. Prefer deleting code that the change makes unused.
5. Most UI flows exist twice: iPhone (`ios/Coconut/*.swift`, e.g. `CoconutApp.swift` root toolbar) and Mac (`mac/Sources/CoconutMac/MacMainWindow.swift`). Put shared logic in an `AppStore` extension and call it from both. The iPhone tab bar always has exactly five tabs (`HomeTab`): a sixth makes iOS add a More tab, which the person does not want, so a new place goes on the page of a tab or takes the place of one. The tabs are Product, Support, Finance, Chats and You, in that order (the person's list; Finance was called Business for a day, and the person named it Finance again), and each holds only its own things: Product the cards, Needs attention, its to-dos and the open pull requests; Support its to-dos and the customer queue; Finance its to-dos (the label `finance`), the overview with the risk reviews, Accounting, Marketing and History; Chats every agent and every chat with people; You the person, this device and the settings (the Mac, notifications, connections, usage, the team, the repositories that Coconut follows). An issue is a to-do of one list, so no tab lists the issues of another (Support shows no queue of all issues, Finance no pull requests). The Mac sidebar has no Product row: the person chose on a card to leave it as it is (2026-11-24), so the Mac's Home keeps the cards and its Support keeps the queue of the product issues; do not add the row or offer it again. On Chats, three or more idle agents of one project fold into a tree under the name of the project (`ChatTree`), which the phone keeps open or closed; a working agent and the chats with people never fold. A conversation with the agent of a project is an agent in every label (New agent, Archive agent, "24 agents" in a tree, the Agents section of the Mac sidebar), and chat names a conversation with people (Team chats, a direct chat) and the tab that holds both; code names such as `HomeTab.chats`, `HomeTab.finance` and `NewChatBar` stay. Buttons and the tint of the app are coconut brown (`BoardStyle.control` in Swift, `accent-color` on the root of the Exact app), and an unread badge is the green of the New line: never black (`Color.primary`) or the system blue, because the person rejects black buttons.
   Nothing links out of Coconut: the person reads, answers, closes and merges in the app, and agents do the same work there. An issue or a pull request opens as `GitHubItemView`, a support conversation as `SupportConversationView` with its answer box, and `stackRoutes` on each navigation stack sends every link of those kinds to these pages (`InAppLink`). Any other web page opens in the browser of the app on an iPhone (iOS 26). A new place that shows a GitHub issue, a pull request or a Gmail thread pushes its route, never `Link` to github.com or Gmail, and a new navigation stack wears `stackRoutes` and `InAppDestinations`.
6. When the change works, rebase onto the latest `origin/main`, `git push origin HEAD:main`, and confirm `git rev-parse HEAD origin/main` match. Revert a change that is confirmed broken, then fix forward.
7. Remove the worktree and its branch. Report: the commit, what changed, what was verified (demo mode vs real Mac service), and whether it has reached the person's devices (see "Releases" below). Never say a push to `main` ships by itself without checking.

## Releases

How builds reach devices changes: read `CONTRIBUTING.md` and `git ls-tree origin/main .github/workflows/` before you promise or trigger a release. Your local checkout can still have workflow files that `main` deleted, and `gh workflow run` then fails with a 422. Do not release: an agent publishes the Mac app and TestFlight builds on a loop a couple of times a day. Say plainly in the reply that the fix is on `main` but not on the devices yet.

## A bug report about the person's own data (counts, read state, lists)

The person sees the installed service, not `main`. Before you write a fix:

1. Grep `origin/main` and `git log origin/main -- <module>` for a recent fix; a rewrite often landed hours ago, and only parts of the request (here a colour) remain to do.
2. Compare with the code that runs: `~/Coconut/backend/coconut/` is the installed service. When it lacks the module or still has the old logic, the cause is the old build. When `coconut status` shows a `Pending install` for hours, check that `~/Coconut/.coconut-install.json` exists: without that marker the app treats the folder as a developer checkout, and `deploy.py` refuses it, so the service never updates.
3. Read the live data read-only: `sqlite3 -readonly ~/Coconut/.runtime/host/coconut.sqlite3` (tables `bots`, `messages`, JSON in `data`). Request results are in `.runtime/host/logs/service.log` as `coconut.request_timing` lines.
4. Prove the fix on real data without touching it: `sqlite3 <live db> ".backup $TMPDIR/copy.sqlite3"`, load the module from the worktree with `importlib.util.spec_from_file_location`, run it against the copy with `/opt/homebrew/bin/python3.14`, print before and after per row, then delete the copy. Put that table in the report.

## The requested feature is already on main

A short request ("Coconut needs to be X") is often for something that landed hours ago but has not reached the person's devices. Step 1 finds it: grep `origin/main` for the feature words and list `docs/` and the top folders of `ios/` (a feature usually has its own doc and target folder). Then build nothing, and answer what the person needs: is it on their Mac and their iPhone?

1. Find the commit and its build number. A build number is the commit count: `git log origin/main --format='%h %s' -- <feature paths>`, then `git rev-list --count <sha>`.
2. Mac: compare with the `Coconut.app` line of `coconut status` (build in parentheses) and with the newest `<sparkle:version>` of `https://coconut-updates.gumroad.workers.dev/mac/appcast.xml`. An installed build at or above the feature's has it. When the feed is ahead of the app, automatic updates install it within the hour (or `coconut update`); check again before replying, since the app often updates while you look.
3. iPhone: a green TestFlight run does not mean an upload. Releases coalesce, so most runs end with the `upload` job `skipped`. Walk `gh run list -R antiwork/coconut -w TestFlight` newest first and read `gh run view <id> --json jobs` until a run has `upload` = `success`; that run's head SHA is what the phone can get. `git merge-base --is-ancestor <feature sha> <run sha>` says whether it holds the feature.
4. Confirm the installed part with evidence, not from the doc: for an app extension, `ls Coconut.app/Contents/PlugIns` and `pluginkit -m -v -i <extension bundle id>`.
5. Report per device: on it now, or which build brings it and whether that upload is running. Add any first-use step that the feature's doc names (e.g. open the app once, enable the extension in System Settings). Say what you did not see with your own eyes (a menu you could not open).

## Rules of the screens

These rules came out of the audits of the screens (the information architecture, the business dashboards and the iPhone app). They hold for each new screen.

- Text is data. A number shows with its name only: no eyebrow, no headline that sells, no note or caption that repeats the title, and no legend for a chart that draws one number for each bar.
- Sentence case in each title, menu and button ("Copy link", not "Copy Link").
- One look for one meaning. The dotted circle is work that runs. A tile that opens a screen of the app has a chevron or nothing, never "↗".
- One loading state and one failed state for each page that loads: `BoardLoading` and `BoardLoadNotice`, with one way to try again.
- A page of tiles is a `BoardPage`. The business dashboards use the one grid and the one tile of `ios/Coconut/Bento.swift` (`BentoGrid`: 12 columns at a Mac width, 2 at an iPhone width), Swift Charts, and the colors of Coconut.
- A pushed page on an iPhone has its title in the bar. The count of a section counts its rows.
- No settings screens. The person changes a setting by asking the Coconut chat (`coconut_settings`); a setting of one device goes in that chat's bar menu or in You. A new preference never gets a screen, a gear or a toggle. A setting that the person asked to change in one tap is a menu row of You that opens its choices in place (`AutoArchiveMenu`, `BoardRow(menu: true)`), and the Coconut chat changes it too.
- No tabs or toggles inside a page (the person, 2026-11-24: "remove the tab/toggle ui. From all pages as no one will tap those"). A page shows one view: no segmented control, no row of filter chips, no tab row of text. Put what a segment hid on the same page, one part under the other or merged into one list with a label on each row (Support's two queues on the Mac, the review queues of Risk, the cuts of History), or keep only the useful default (the last 30 days of Usage, the open work and the open conversations). A choice that a form needs to work (the project of a new to-do, a notification level) is a menu, not a tab. The tab bar of the iPhone and the sections of the Mac sidebar are places, not tabs of a page.
- A Send of the message box (`NewChatBar`) never opens the chat that it makes. The chat shows at once near the top of the Chats list (in the open tree of its project when the project folds) and under its project in the Mac sidebar, and the box keeps the keyboard and the cursor, so the person can queue up many chats in a row (`AppStore.newChatSend`, `NewChatReveal`, and `afterStart` in `exact/app.contract`). A message on its way to the Mac counts as activity of its chat (`ChatSummaries.sending`), so the next Send never reuses a chat whose first message has not arrived yet. Send to a new agent inside a chat (Option-Return on the Mac, the menu of the Send button, also in a chat that archived itself) goes through the same `AppStore.sendNewChat` and keeps the person in the chat they are in, with the keyboard, so they can fire off side tasks without leaving it (the person's choice on a card). The menu of a queued message has it too (the person: "Add send to new chat to hold send and from queue menu"): the message leaves the queue with its files once the new chat has it, and stays when the send fails (`AppStore.sendQueuedToNewAgent`). The Mac takes the files of another chat of the same agent for this (`_validate_attachments`, `AgentChats._same_agent`).
- Idle and Archived are one (the person: "Merge idle and archived", and again on 2026-11-24). The Chats list of the iPhone (`ChatList.all`) and the Agents list of the Exact app (`fromSnapshot` in `exact/app.ts`) show every chat in one list with no Working and Idle tabs, put an archived chat among the others by its newest activity, with no Archived row or page, and its swipe and its card in the deck offer Unarchive. Many idle agents of one project fold into a tree (`ChatTree`); a working one never folds. The Mac sidebar keeps its Archived section, which the person kept with the sidebar's other sections.
- A chat archives itself after the time of the setting `auto_archive_hours` (48 hours until the person picks another, 0 for never): `AgentChats.archive_idle_chats` on the Mac, `PUT /v1/settings/auto-archive`, the row Auto-archive of You, and `auto_archive_hours` of `coconut_settings`. Both states carry it (`Snapshot` and `NativeSnapshot`), and a change sends `settings.updated`, so every device shows the new time.
- A form edits and a board reads: a form (Your Mac) is a grouped system form, and a board is sections on paper.
- A time next to what an agent does is the time of that step, its last action (the person: "time stamps should match the last action"). The working line and the row of a working chat in the Chats list count from the start of the newest step (`phase_started_at`, through `AppStore.runningPhase`), to the second and live: a web search that began 23 seconds ago says 23s on both, however long the turn has run and however old the newest message is (`ChatRowLayout.step`, `StepTimeLabel`; `step` of `ChatRow` in `exact/`). A row that shows a message or a card keeps the age of its newest message.
- The business screens compute nothing: no total, change or margin in the client (`BusinessHomePresentation`). A missing value shows as "—" or "Not published", never as zero. A failed or stale source never reads as "All clear".
- The rules of "Needs attention" live in one type, `AttentionRules` (`ios/Coconut/Attention.swift`), with named thresholds. The service counts the same rules for the number on the app icon (`backend/coconut/app_badge.py`): change both together.
- The Usage page is a leaderboard by person first: the person asked for usage by person, with the leaderboard as the crux to optimize use. The people of each team rank by cost at the top (`UsageBoard`, `UsageLeaderboard`, from the `usage` entries of the team log, `backend/coconut/team_usage.py`), and the usage of this person comes under them. Without a team the projects are the leaderboard.
- Usage is about cost first and tokens second (the person: "Token usage should be about cost first tokens second"). Each place that shows usage leads with what it cost and puts the tokens after it: a place on the leaderboard shows its cost large and "18.2M tokens · 412 turns" under it, the charts are spend by day, the spend leads the numbers of a project and of this person, models list their cost before their tokens, and the last row of a chat reads "$2.41 · 184k tokens". The tokens lead only where Hermes has no price for the models (`UsageLeaderboard.metric`). A new place that shows usage follows the same order.
- To-dos are issues of `antiwork/gumroad-private`, and nothing else holds one: no other repository, no chat and no card of Coconut. The person keeps three lists, Product, Support and Finance, each on the tab of that name with its own count (`TodoArea` and `TodoCounts` in `ios/Coconut/TodoLists.swift`, `backend/coconut/github_todos.py`). The label of an issue names its list (`finance`, `support`, `product`), so GitHub shows the same split; an issue without one is a to-do of Product. A new place that shows to-dos shows one list and counts it on its own tab, never a mix of the lists, and new work of a function goes to the same repository with the label of its list (`business.WORK_AREAS`). Cards stay Coconut cards: they show on Product and count on no tab. The person chose this on 2026-11-23 over a design that moved each card into a gumroad-private issue, so do not build that move or ask about it again while its facts are unchanged.
- The list of to-dos of Product, Support and Finance has no title and no count over it: its rows say what they are, and the badge of its tab counts them (the person: "Don't have to say todos in the ui the table itself is self descriptive"). Product lists its rows under the cards (`productList` in `HomeViews.swift`), and Support and Finance put them in a section without a title (`TodoListSection`). An empty list keeps its sentence ("No to-dos. Tap + to add one."), because then no rows speak for it.

## Check by hand

The repository has no tests, and `AGENTS.md` asks for none. Check the change by hand before the push.

The iPhone app: `python3 scripts/qa.py <place>` builds what changed, installs it in its own simulator ("Coconut QA") and opens the app on one screen with demo data. `qa.py open <place>` opens another screen without a build, and `qa.py shot [file]` saves a screenshot. A place is a name of the `--open` launch argument (`showPreviewPlace` in `ios/Coconut/CoconutApp.swift`). Further launch arguments: `--team-preview` (a team with notices), `--attention-preview` (Needs attention), `--bottom` (the end of a page) and `--scrolling` (a chat during a scroll). The same steps by hand, in your own simulator:

```sh
xcodegen generate --spec ios/project.yml            # after adding a Swift file
cd ios
xcodebuild build -project Coconut.xcodeproj -scheme Coconut \
  -destination 'platform=iOS Simulator,id=<udid>' -derivedDataPath $TMPDIR/dd CODE_SIGNING_ALLOWED=NO
xcrun simctl install <udid> $TMPDIR/dd/Build/Products/Debug-iphonesimulator/Coconut.app
xcrun simctl launch <udid> com.gumroad.coconut --demo
xcrun simctl io <udid> screenshot $TMPDIR/shot.png
```

- Pipe xcodebuild through `grep -E " error:|BUILD (SUCCEEDED|FAILED)"`; full output floods the context.
- Run one xcodebuild at a time, and shut your simulator down when you finish: many agents share this Mac.
- Never launch the debug Mac app: it has the installed app's bundle ID. Never drive the desktop (mouse or keyboard): the person uses this Mac.
- Demo mode skips the Mac service; say so when reporting, with what you checked by hand and what you did not.

The service, the plugin and the scripts:

- Run `/opt/homebrew/bin/python3.14 -m compileall -q backend hermes_plugin scripts`, then import each module that you changed. The system `python3` is 3.9 and fails at import.
- Call the functions that you changed against a backup copy of the database (step 4 of "A bug report about the person's own data"), never the live file. Do not build a whole `Service` for that: it starts the team sync and talks to the relay. Call the method unbound with a small stand-in for `self` that has `db`, `_all`, `_put` and `_event`.
